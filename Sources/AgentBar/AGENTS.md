# AgentBar — agent notes

Native Mac agent switcher (⌥Tab panel) over the AptusFit **chief dashboard** (`127.0.0.1:4711`). Separate app/target from FastTab; shares only `CommandBarKit`. Rules: edits stay in `Sources/AgentBar` + `Tests/AgentBarTests`; `FastTab` / `CommandBarKit` diffs must be empty unless the task says otherwise.

## Build / test / run
- App: `scripts/build-agentbar-app.sh --open` (→ `dist/AgentBar.app`). Do this after every change.
- Tests: `swift test --filter AgentBarTests` (~1377). Full-suite runs flake under machine load; re-run the failing test alone before believing it (known: `FastTabTests.licenseServiceRecoversWhenInitialStorageLoadFinishesAfterTimeout` under parallel load — passes solo).
- Own defaults domain `com.trungluong.AgentBar`. Unsandboxed.

## What it does (user vocabulary → code)
| User says | Code / concept |
|---|---|
| "Needs you" | generic: agent live and not working, until Done or Park |
| "Blocked" row | dashboard `needsYou` kind `question` (picker) / `blocked` (permission box) |
| **Answer** button | red; opens answer card for a parsed picker (`Answer/`) |
| "the terminal shows tabs ← ☐ Q1 ☐ Q2 ✔ Submit →" (agent asked several questions at once) | **form card** (`Answer/Form/`, `AnswerCardModel+Form`): ONE card with every question + options + Other; one Submit, enabled only when every question is answered |
| **Review** button | red; opens permission card: Allow / Allow always (2nd press) / Deny (`Permission/`). On a **plan** box (below) it opens the plan card instead |
| "plan mode box: Claude has written up a plan… Would you like to proceed?" | **plan card** (`Permission/Plan/`, `Panel/PlanCardView`): the permission card's shell with the PLAN itself (rendered from the plan file) and the box's own rows verbatim (e.g. "Yes, and use auto mode" / "Yes, manually approve edits" / "Tell Claude what to change"); `PermissionPrompt.kind == .plan`, dashboard `row.permission.kind == "plan"`, `POST /api/permission {choice:"select", index, text?}` |
| **Open terminal** | fallback when the box can't be parsed / non-Claude agents |
| Done / Park | triage (`Triage/`); Done = dashboard stop then close (two steps); Park persisted |
| "peek at bottom-right" / "hover the corner" | **corner tab** (`Corner/`, setting `showsCornerTab`): slides in for ~5s when an agent newly needs you, and when the pointer rests ~0.3s in the bottom-right screen corner (`CornerHotZone`); **hover never opens the panel, a click does**. **Sticky while any Needs-you agent is blocked** (Answer/Review rows): red dot + "waiting for your answer", no 5s timer, no leave-grace; ends on click / panel open / setting off / last blocker handled (then the normal ~0.7s grace). A generic tab that turns out blocked becomes sticky; one already gone re-shows once per agent stay (`BlockedEpisodeTracker`, machine event `needsYouChanged`). NOT Space-to-peek (`Peek/`, `PanePeek`) |
| "the question/permission screen shows directly at the corner instead of the chip" | **corner card** (`Corner/CornerCardView`, `CornerTabContent.soleCardableAgentID`, machine effects `showCard`/`updateCard`, gotcha 16): when exactly ONE agent is blocked with something AgentBar can render (question, reviewable permission, plan, multi-question form), the corner window shows that agent's live Answer/Review card instead of the pill; two or more blocked, or a lone blocker with no card (`questionLoading`/`questionNotAnswerable`/plain `permission`), keeps the pill |
| "sound for needs answer / agent done" | **`Sound/`**: `ArrivalSoundPlanner` (pure) + `ArrivalSoundController`; Settings > General > Alerts (`SoundSettings`, own defaults): Needs you = Funk (blocked: question / permission), Agent done = Glass (plain finish); each a pick of the 14 system sounds or None; picking previews |
| **Message** button | grey; opens the message card (`Message/`): type one line into a Claude agent's terminal without switching to it. Shown on Working rows, generic Needs-you rows (no blocker) and Parked rows that are not blocked; last in the row, so →/← order of Done/Park is unchanged; keyboard = ← → to highlight, ↩ to open, ↩ to send |
| **Copy** button / ⌘C | copies the agent's name, pane ID, project, folder, session (`Copy/AgentIdentityText`); on both cards' headers, on the hovered row, and ⌘C in a card (only while the search box has the keyboard, so text fields keep normal copy) |

## Data source
- `/api/events` (SSE) → `/api/state`; actions: `POST /api/focus`, `/api/session/{stop,close,message}` (actor "po"), `/api/answer`, `/api/permission` (`allow|deny|allow-always` on tool boxes, `select` on plan boxes); `GET /api/pane/screen?paneId=` (read-only, ~2.5s).
- Never herdr `agent_status`. **Never POST to the real dashboard in tests** — use a fake dashboard on another port.
- Detection lag ≤15s (screen sweep). Dashboard row flaps between parsed picker / hook preview / plain blocked → `BlockerMemory` (45s) keeps Answer/Review steady.
- **Answer/Review lag fix (`BlockerProbe`)**: when a row is in Needs you with no parsed blocker (none / loading options / plain blocked), AgentBar itself does the read-only pane GET, parses it (`PaneQuestionReader.question`, `PanePermissionReader.prompt`) and feeds the result to `BlockerMemory.learn`. One read per arrival; dashboard-blocked rows retry at +2s/+5s (max 3 reads), silent rows read once; results for a row that moved on are dropped. The probe is plan-aware: `PanePermissionReader.prompt` = `parse_permission_or_plan_block` (tool box, else plan box). The question parser is a port of `parse_question_block` (differential fixture `Fixtures/question-screens.json`, generated by running the real Python; `context` is not ported, the card uses the transcript). The corner tab text is NOT delayed for this (it says only "N need you").

## Gotchas (each cost a live-check round)
1. **Wrapped screen vs exact match.** Feed shows the screen as drawn (wrapped/cut); `/api/answer` and `/api/permission` match the *unwrapped* text exactly. AgentBar does a **pre-send read** (GET pane, re-parse, echo the pane's version). Parsers are Swift ports of the dashboard's Python (`parse_question_block`, `parse_permission_block` in AptusFit `scripts/lib/classify_pane.py`), differential-tested against real Python via fixtures (`Tests/AgentBarTests/Fixtures/*-screens.json`). If the dashboard parser changes, regenerate fixtures and re-port.
2. Card error "unknown command: herdr" = the *dashboard* pane read is broken/stale, not AgentBar. Restart the dashboard after pulling AptusFit changes (old process keeps old code).
3. Dashboard collapses newlines to spaces (500-char cap): Shift+Enter in the custom answer is a visual newline only.
4. Feed decoding is per entry (`unreadableFeedNames`); one odd key (e.g. `machinesConfigError: null`) must not fail the whole state → false "status feed down".
5. Latest message: tail of `~/.claude/projects/*/<agentSession>.jsonl` (last assistant text block; transcripts reach 130MB, tail-read only). Plan link = best-effort last existing `.md` `file_path`, skipping SKILL/CLAUDE/AGENTS/README/MEMORY.md and /tmp. The message is drawn as markdown by `Markdown/` (own block parser → `MarkdownBlocksView`; input capped at 20k chars; collapsed to ~5 lines with Show more, measured not estimated; only http/https/mailto links are clickable).
6. Send closes the card at once; the row shows a spinner (20s safety timeout); failures show verbatim in a red notice above the footer that stays until the user closes it (✕ or Esc; Esc dismisses it before it closes the panel / backs out). A newer failure replaces it; summoning the panel does not clear it. The orange shortcut-problem strip is separate and not closable. The ✕ once did nothing with the mouse: a tint drawn with `.overlay(Color)` above the notice swallowed the click (esc worked). Never put a hit-testing overlay over a control; `FooterNoticeViewTests` sends real mouse events to the ✕.
7. Alt-tab release = 20ms poll of `NSEvent.modifierFlags` (non-activating panel, no Accessibility permission).
8. **Sound classification hold.** Dashboard `blocked` arrives up to ~15s after the row, and `BlockerProbe` a few seconds after an arrival, so an unclassified arrival is held `ArrivalSoundPlanner.holdSeconds` (4s) before playing "done"; a blocker learned meanwhile plays the answer sound instead, an agent that leaves plays nothing. One sound per reading (answer wins). Fed by `onNeedsYouReading` (same detector as the corner tab: baseline readings are silent); a blocker seen after the hold is not retroactively sounded (the corner tab, which is not held, still goes sticky).

9. **Multi-question form card.** One AskUserQuestion call with 2+ questions = tabs in the terminal, but the dashboard's `/api/answer` only answers the tab on screen. The card therefore reads the agent's **transcript** for the pending call (`AskUserQuestionExtractor`, tail-scan: newest AskUserQuestion `tool_use` with no later `tool_result` carrying its id; `SessionTranscriptReader.pendingQuestionForm` widens the tail window) and, when the pane's question text matches one of its questions (`PendingQuestionForm.indexOfQuestion`: by text only, never by ☐/☒/✔ glyphs, whose meaning is unconfirmed), the card turns into the form a moment after opening (`AnswerFormState` holds the drafts; a click-driven card, Enter submits, Esc goes back). No session / transcript / matching form / a 1-question form = today's single card, untouched. Card identity while a form is open is the form itself (`toolUseId`): `reconcile`/`follow` never replace it while it is sending or stopped, and a tab change of the same form is not a new question.
10. **Batch send is NOT atomic, and never retried.** Submit runs `FormBatchDriver` (pure `FormBatchPlanner` + thin async loop): per question read the pane (read-only) -> find the on-screen question in the form by text -> verify the chosen option labels against the pane (exact label first; a label cut short by the pane matches only when exactly one row could be meant; "Yes" never picks "Yes, and remember") and use the pane's own option numbers -> `POST /api/answer` for that one question -> the next read confirms the pane moved on (bounded reads, then a stop; whole-batch budget 40s per question via a watchdog that cancels the task). After the last question the dashboard presses "Submit answers" itself. A question the terminal has already moved past is **skipped and named** in a footer notice (it may have been answered in the terminal, or merely never visited: tabs can be navigated). Any refusal/timeout/unexpected screen stops the batch: the card stays with the exact report (which landed, which did not, the dashboard's words), a footer notice repeats it, and **no resend is offered** (a resend would toggle multi-select ticks off). The row shows "Sending answer…" from the first press (one `AnswerSendTracker` flight for the whole batch; `alsoAnswered` covers every tab the lagging dashboard may still show, so no fresh single card reopens). Closing the panel mid-batch does not cancel it; its failure still reaches the footer. Reopening after a partial send works: the terminal is past the landed questions, so they are skipped, not resent, but the user must re-answer them in the new card (unknown from the pane whether they were answered).
    - **"Not attempted" may mean already recorded.** The dashboard's own answer path once sent a stray Enter after a typed Other answer (lands on the next tab's option 1 and advances/submits the form; brief `.claude/briefs/dashboard-answer-stray-enter.md`, fixed on the AptusFit side). So a batch that reads no question after a landed answer (`.paneShowsNoQuestion`) asks the **transcript** (`SessionTranscriptReader.recordedAnswers`: the `tool_result` for the form's `tool_use` id, text `The user answered: "Q"="A", …` and `toolUseResult.answers`, keyed by question text): if it recorded answers the report is "The form was submitted. Recorded answers: …" and any answer that differs from the user's draft is flagged ("You chose X but the terminal recorded Y — check it"; outcome `.recorded(answer:chose:)`). Looked up a few times (the result line lags the terminal). Transcript can't tell = the old stop, worded "may already be submitted or being answered in the terminal".
    - **Exit-row state.** `PaneQuestionReader.openPickerState` = `.open` / `.onExitRow` (cursor `❯` on `Submit`/`Next`: no `❯ <digit>.` line exists) / `.hasTicks` (a multi-select option already ticked) / `.unparsed` / `.review` / `.none`. `question(in:)` stays answerable-only (nil for the other states); `identity(in:)` counts every open picker (the Message pre-send guard relies on it). `.onExitRow`/`.hasTicks` on a step = someone is answering this question in the terminal: stop, never typed into, never retried (unless the read is a stale redraw of a question already answered, which is waited out). Rows after the exit row (`Chat about this` is drawn last) are never options.

11. **Message card** (`Message/`; `POST /api/session/message {rowId, actor:"po", text, confirm?}`, ~2s+ server side so 60s timeout). The dashboard refuses empty text, **any newline**, a **leading `/`**, >2000 chars, non-live rows, its own pane, a pane with an open question picker or permission box; a busy pane answers `needsConfirm` until resent with `confirm:true`. AgentBar mirrors that up front (`MessageDraftValidator`, pure): **newlines are collapsed to one space on send** (Shift+Return only shows a line break; the card says "Line breaks are sent as spaces"), **slash commands are refused inline**, live counter from 1800/2000. Before every send it does its own **pane read** (`PaneQuestionReader` + `PanePermissionReader`): an open picker/box = nothing sent, "This agent is waiting on you — answer it first" (typed text would answer/deny it). **Confirm-on-busy**: `needsConfirm` keeps the card open and turns Send into a second press ("Send anyway"), which alone carries `confirm:true`; editing the text drops the arming. **No retry ever**: a timeout/unreadable reply says "may have gone through — check the terminal" and offers a manual "Send again"; the card ignores Esc while a message is on its way, and a reply for a card that is gone goes to the footer notice. Success closes the card and the row says "Message sent" / "Message queued" (from the reply's `state`) for ~6s in place of its buttons (`sentLabel`). Only rows with `hasHookData` (Claude) get the button: for opencode/codex/gemini the dashboard's classifier is blind, so its permission/question guard cannot protect them. A reply "NOT SUBMITTED" / "mid-sequence" (the dashboard never clears the typed text) is `.uncertain`, not a plain failure: a second Send would type the text twice (`textMayBeInInputBoxWords`). The pre-send guard asks whether ANY picker is open (`PaneQuestionReader.identity`), not whether one is answerable (a picker with a ticked option is not). Drafts live only while the card is open. Text focus for the card lives in one place, `MultiLineAnswerField`/`AnswerTextView`.
    - **`/compact` and `/clear` are allowed exceptions to the slash-command block** (2026-09-22, client + dashboard server both updated together). `MessageDraftValidator.check` matches these two **exactly**, and **asymmetrically**, mirroring the dashboard's `is_allowed_slash_command`/`_ALLOWED_SLASH_PREFIX` exactly: `/compact` alone, or followed by `" "` and more text (`/compact keep the plan`); `/clear` **bare only** — `/clear starting fresh` still refuses (QA'd 2026-09-22: the first cut let `/clear` take trailing text too, which the dashboard would then have bounced as a plain slash command after the client had already told the user it was ready). Never a prefix match either way, so `/compactfoo`/`/clearish` still refuse. Everything else leading with `/` is still refused, typed into the card or Shift+Return-routed or Tab-tagged (all three go through this same `check`). This means the exception applies even to these two commands typed by hand into the Message card, not only to the row menu's own Compact/Clear shortcuts (next gotcha) — those two bypass the validator entirely rather than relying on it.

12. **Dictation / activation (`Focus/`).** Dictation tools (Wispr Flow, Superwhisper, macOS Dictation) type into the **frontmost app**; AgentBar is an accessory app with a non-activating panel, so it took keystrokes as key window but was never frontmost and dictated text went to the previous app. Fix = `TextInputActivation` (pure logic, `AppFocusing` protocol + `FakeAppFocus` in tests; `SystemAppFocus` is the real one): AgentBar **activates itself only when a card text box appears** (`AnswerTextView.didAppearNotification`, posted from `viewDidMoveToWindow`; Answer custom field, form Other field, Message field all use it, so the rule lives in one place). The **plain ⌥Tab list and search stay non-activating** on purpose: `ModifierReleaseWatcher` polls `NSEvent.modifierFlags` and needs no activation, and activating mid-cycle would steal focus from the app the user is switching away from. If the summon modifier (⌥) is still held when a text box appears, activation waits (50ms poll) until it is released; a ⌥-release commit or close cancels it. **Restore rule**: on panel hide, `previousApp.activate` only if AgentBar was the one that activated, has a previous app that is alive, and is *still frontmost* (user did not move on). Activation stays until the panel hides (it is not undone when only the card closes: deactivating would drop the panel's key status and break search typing). **Click-outside while active**: the global mouse monitor no longer sees other-app clicks, so `NSApplication.didResignActiveNotification` hides the panel and calls `appResignedActive()` (no restore: the user chose that app). Settings and agent-switch hides pass `restoringFocus: false` (they bring their own window forward). **Failed agent switch**: the switch hide passes `isAgentSwitch` (`panelDidHide(handingOffToAgentSwitch:)`); if the panel returns with AgentBar still frontmost, the remembered previous app is adopted again so Esc hands the front back (a successful switch, terminal frontmost, forgets it; a Settings hide never hands off). Opt-out: `defaults write com.trungluong.AgentBar activatesForTextInput -bool NO`. **Unverified** (no headless way): a real dictation tool typing into the card; ⌥Tab from a full-screen Space (panel is `.canJoinAllSpaces` + `.fullScreenAuxiliary`, activation should not switch Spaces); focus return in real apps; macOS 14 cooperative activation may refuse `NSApp.activate` in some situations (then nothing breaks, dictation just behaves as before).

13. **Plan card** (Claude plan mode; `Permission/Plan/`, `PermissionCardModel+Plan`). Same `PermissionCard` shell (`card.plan` set = plan card; `card.state` is then dormant). Parser = Swift port of `parse_plan_approval_block` (`PanePermissionReader+Plan`), differential-tested against AptusFit's verbatim `Fixtures/aptusfit-permission-screens.json` (real captures + variants; re-copy that file if the Python changes). `PermissionPrompt` gained additive `kind` (`.tool`/`.plan`) and `planPath` (verbatim, `~` unexpanded; part of `PermissionIdentity` because a plan box's title/rows are one fixed sentence for every plan). Rules that each cost thought:
    - **Rows are the box's own words**, never hard-coded; buttons/rows come from `options`. **Nothing preselected** (not even the terminal's cursor row); Return with nothing chosen does nothing. A plan box offers NO allow/deny choice (`option(for:)` is nil for plans): its "Yes…" rows only look like allow rows, and the server would press row 1 (auto mode) for an "allow".
    - **Privilege change = second press.** A row whose label contains "auto mode", "auto-accept" or "bypass permissions" (`PermissionPrompt.isPrivilegeChange`, label-based, ignores case, hyphens, runs of spaces) arms on the first press ("This puts the agent in auto mode — press again to confirm"); any other key/click cancels. Unknown wording gets no second press: the server still verifies the labels. A held Return never does the second press (`activateSelected(isKeyRepeat:)`, `AnswerTextView` ignores repeats).
    - **Feedback row** = first row starting "Tell Claude", else the last row unless it says "Yes" (`feedbackOption`); the server accepts `text` only on a row containing "Tell Claude what to change" and refuses otherwise (shown verbatim). Enter/click on it opens a `MultiLineAnswerField` (dictation works through `TextInputActivation`); Return sends, Esc back to rows (draft kept); blank feedback never goes; newlines collapsed, capped at 500 like the server. The dashboard types it then submits with **Enter** (AptusFit 96160f4; never shift+tab: the box's own footer hint "shift+tab to approve with this feedback" APPROVES the plan into auto mode). Live-proven through AgentBar 2026-09-20: transcript shows the plan tool rejected "the user said: <feedback>", the agent writes a revised plan and a new plan box, the pane never leaves plan mode; the card says so (`PlanCardState.feedbackNote`). A `{ok:true,warning}` reply (pane unexpectedly in auto mode after a non-auto choice) is never swallowed: orange closable footer notice "Sent, but the agent now shows auto mode: … Check the terminal." (`PanelFooterNotice.warning`) and, if a card for that agent is open, the same line on it (`PermissionCard.sentWarning`). `PermissionResult.sent(next:warning:)`. Not covered by the dashboard guard: a LATER revised box can land in auto mode by itself; not reproduced live (the revised box sat unanswered 57s, pane stayed plan mode).
    - **Last look at the pane at send** (`PlanSend.deliver`): read the pane again; only if the plan box (file + row wording) is unchanged, POST with the pane's own copy; else "Nothing was sent: the plan prompt … changed". The card closes at once, row says "Sending your answer…"/"Sending feedback…". Never retried; no reply in 20s = "may have gone through". A kind mismatch (tool box where a plan card was opened, or reverse) is never adopted.
    - **Plan file** (`PlanFileReader`): `planPath` read from the pane, `~` expanded against the local home, `.md` only, absolute or `~` paths only, read-only, first 200KB (cut on a character boundary, "longer than 200 KB" note; the Markdown renderer additionally cuts at 20k chars with its own note). Read on a background task; missing/unreadable/empty/no path = the plan-less card with the reason, approval never blocked. Local file only: a plan on a remote machine's pane reads as missing or, worse, a same-named local file.
    - Send body echoes `detail:null`, `kind:"plan"`, `planPath` (null when absent) and every option label; the dashboard's `_same_permission` compares each.
    - The Message card's pane guard uses the same reader, so typing to an agent sitting on a plan box is refused.
    - **Herdr panes are 76 columns wide and the box wraps its own text** (the "unwrapped" read does NOT undo it: Claude wraps with real newlines). Title = 1-3 consecutive rows (a blank row does NOT stop the join, like Python's `_join_wrapped_lines`) joined with single spaces and matched against the exact sentence; the footer row must have a blank row above it and be the ONLY such row (two candidates = ambiguous = `planPath` nil, never last-wins, AptusFit b4d8a1d); the path is whole on the footer row or, when that row ends at the `·`, on the next 1-3 rows joined with no space (`.md` only, else nil; a path begun on the footer row that wraps reads as nil, as in Python). Edge cases pinned in `PlanApprovalPythonParityTests` (expected values taken from running the Python 2026-09-20). The echoed `title` is the JOINED single-space sentence, equal for wrapped and wide drawings (`_same_permission` compares it exactly). Real captures: `Fixtures/plan-box-narrow-*.txt`, tests `PlanApprovalWrappedTests`. Python side: AptusFit brief `.claude/briefs/dashboard-plan-box-wrapped.md`; **Swift and Python must join rows identically** — if the Python worker's normalisation differs from this, re-port. **Still unwrapped on both sides** (proven with a real edit-box capture at 76 cols, `PanePermissionReaderTests`): tool-box option rows longer than the pane (e.g. "Yes, and allow Claude to edit files in this project's .claude folder for this session") keep only their first row, so Allow always vanishes; a tool title wraps only for a 41+ character file name. Fix both parsers together or the labels will differ and sends get refused. Question text rows are already joined by `PaneQuestionReader`.

14. **Typed text is control-free** (`TerminalSafeText`): message, free-text answer and plan feedback drop control characters (tab becomes a space): an ESC/Ctrl-C in pasted text would be a keystroke in the agent's terminal. Form batches are tracked per agent (`batchTasks`/`batchWatchdogs`): a watchdog cancels only its own batch.

## Live-check protocol (what worked)
Test against a real agent pane in a scratch herdr tab (e.g. `test-perm`); prefer **Deny**/no-op choices on real boxes; verify dashboard behaviour with GET only.

15. **QA pass 2 rules.** The corner machine forgets the pointer position whenever the panel opens or closes (the host stops watching the pointer meanwhile, so a stale "on the tab" once removed the 5s timer / gave the next arrival a 0.7s tab). Small orange TEXT uses `WarningTextColor` (system orange is ~2.2:1 on light); orange stays fine as a fill or dot.

16. **Corner card** (the corner tab shows the blocked agent's actual question/permission screen instead of the pill). Decisions (PO, 2026-09-21): all blocker types inline (question, permission, plan, form), typing focuses only when the user clicks a text field, and two or more blocked agents fall back to the pill. Rules that each cost thought:
    - **Same card, same model.** The corner does NOT build its own card: `AgentPanelModel.openCardForCorner(agentID:)` opens the shared `answer`/`permission` card exactly as the row's Answer/Review press would, and `CornerCardView` (in `CornerTabView`'s `card` mode) just draws `AnswerCardView`/`PermissionCardView` from that model. So form batches, plan feedback, the pre-send pane read and footer notices all apply unchanged. A repeat call for an agent whose card is already open is a no-op (never resets a draft). `reconcile` (every status read) already closes the card when its blocker goes; the corner additionally closes it via `closeCardOpenedForCorner()` when it leaves card mode (second blocker, setting off).
    - **Machine only changes the effect, not the rules.** `CornerTabMachine` emits `showCard`/`updateCard` instead of `showTab`/`updateTab` when `content.soleCardableAgentID` is set (computed in `CornerTabContent.forArrivals`: exactly one blocked agent and its blocker is `.question` or `.permissionReview`). Sticky, timers, click and the "hasNewBlocker" gate are untouched (so, as before, a blocker already known when the panel is closed again does not re-show the corner until a NEW blocker arrives). The hover summary (`showSummaryTab`) also checks the summary for a sole cardable agent (an agent already blocked at launch).
    - **Panel hand-off starts the panel clean.** Opening the main panel (hotkey, or the card header's expand button / a tap on the header = `tabClicked`) removes the corner window; the panel's own `resetForShow` closes the card, so an unsent draft is dropped (deliberate: KISS; a real hand-off would need `resetForShow` to skip it). On the hotkey route `leaveCard(isPanelOpening: true)` drops only the corner's bookkeeping (no `panelDidHide`: the panel already owns the activation session, and the flag is not a counter); the click route (header/expand) passes `isPanelOpening: true` too. `showTab`/`updateTab`/`setEnabled(false)`/✕ close the card.
    - **No card = pill, never an empty card.** `openCardForCorner` returns false when there is nothing to show (agent gone, answer in flight, no pane); `CornerTabController` then shows the plain pill. It looks in every shown agent (not the searched list). After a Send the card closes at once, so `showPillIfCardEmpty` (run after every model change, so Send/Esc empty the card at once) tries to reopen (e.g. blocker changed question->permission), else puts the pill in place until the dashboard catches up. Failed corner-driven opens are silent (`isOpeningCardForCorner` mutes the footer notices). The click on the header/expand goes `isPanelOpening: true` too, so activation is not restored to the previous app mid hand-off.
    - **Window.** Same non-activating `TabPanel`, now `canBecomeKey = true` with `becomesKeyOnlyIfNeeded = true`: a click on a button/option row never makes it key (nothing steals the keyboard), only a control that needs it (a text field's `becomeFirstResponder`) does. Card mode uses `CornerTabPlacement.cardWindowFrame` (panel width, header + divider + `AgentPanelMetrics.fullBodyHeight()` + footer, bottom-right anchored, grows upward, shadow on), the pill keeps `windowFrame`. A pill<->card change while the window is up is shown like a fresh appearance (`CornerTabWindowController.update`/`updateCard`).
    - **Dictation while the card is up.** `CornerTabController.openCard` starts the SAME `TextInputActivation` session the main panel uses (`panelDidShow`, and its own `AnswerTextView.didAppearNotification` + resign-active observers, since `AgentPanelController`'s are registered only while ITS panel is visible); `closeCardIfNeeded` ends it (`panelDidHide`). Card text fields only appear after a click ("Other" row, plan feedback row), so activation still happens only when the user clicks in. The main panel and the corner card are never visible together (the machine removes the corner when the panel opens), so they share one activation instance safely. **Unverified live** (no headless way): a real dictation tool typing into the corner card; ⌥Tab from a full-screen Space with the card up.
    - **Dismiss ✕** (on the pill and the card header, `CornerDismissButton`). `CornerTabEvent.dismissed` -> phase idle + `slideTabOut` (the controller closes the card, as for any slide-out). It does not answer or open the panel; the agent stays blocked in the panel. Because the machine is idle again, the `hasNewBlocker` gate keeps the same blocker from re-showing; a NEW blocker, or resting the pointer in the corner (hover summary/card), brings it back. `CornerTabMachine.dismissedCardAgentID` (sent by the controller with the event) keeps an unrelated arrival from re-summoning THAT agent's card: the pill shows instead, until it gets a new blocker, nothing is blocked, or the pointer rests in the corner (an explicit summon clears it). A different agent blocking still gets its card. After the user leaves AgentBar while the card is up, dictation into the same text field does not re-arm (needs the field to appear anew). Unsent typing is lost on ✕ or when a second blocker swaps the card for the pill.
    - **Known limits.** A failure notice that is not dismissible (the shortcut-problem strip) shows in the card's footer; dismissible ones float over its bottom like the panel's. Keyboard arrows/Enter in the corner card only work once the window is key (after clicking a text field); the mouse works always. The window height is clamped to the display, but the card's own height is not (on a display under ~630pt visible height the header/footer clip); the body height is the default row count, not the user's max-rows setting.

17. **The row's ⋯ overflow menu** (`RowMoreMenuView.swift`, 2026-09-22) — **first overflow-menu precedent in AgentBar**; follow this shape rather than invent a second one. Done and Close pane moved out of the plain capsule strip and into this menu, alongside two new quick commands, Compact and Clear (send `/compact` / `/clear`, gotcha 11). What each part is:
    - **Data model.** `RowButtons.available(for:)` is now the capsule strip ONLY (Answer/Review/Open terminal/Park/Unpark/Message, ending in `.moreActions` when the menu has anything usable) — Done and Close pane are no longer in it. `RowButtons.menuItems(for:)` is a second, independent list: Done and/or Close pane (whichever this row's section would have offered as a loose button before) plus Compact/Clear when the row is message-eligible (same gate `messageButton` uses, factored into `isMessageEligible`). The `.moreActions` trigger itself only appears when at least one menu item is enabled (`moreActionsButton`) — never a menu that opens onto nothing but a disabled row.
    - **Press authorization is a separate concern from where a button renders.** `AgentPanelModel.press(_:on:)` used to gate on `usableButtons(for:).contains(button)` (the capsule-strip list); that would now reject a menu selection of `.done`/`.closePane`/`.compact`/`.clear` outright, since none of those are in that list any more. Fixed with `RowButtons.isPressable(button:on:)`, which checks BOTH lists (`available` and `menuItems`) — a menu item is authorized the same way a capsule tap always was. `RowButtons.usableButtons(for:)` itself is unchanged and stays capsule-strip-only: it is what ←/→ keyboard traversal uses, and the ⋯ trigger is the deliberate last stop on that list (Message stays the stop before it — same "Message is last" precedent, just one slot earlier now).
    - **Done/Close pane still go through `RowActionMachine`/`AgentPanelModel.press`, unchanged** — a menu selection calls `model.press(.done, on: agentID)`, exactly what a capsule tap always called. The confirm-on-second-press flow (`RowActionState.confirming`) is untouched. Compact/Clear are different: `RowActionMachine.plan` maps them straight to `.sendQuickCommand("/compact" | "/clear")`, which `press` hands to `message.sendDirect(to:text:)` directly — no `MessageDraftValidator` call (these two exact strings are pre-approved), no confirm step, no card. `.moreActions` itself maps to `.ignore`: it is never "pressed" through this machine (see next point).
    - **Enter on the highlighted ⋯ trigger cannot open it.** There is no public SwiftUI API to pop a `Menu` open programmatically, and AgentBar's ←/→ + Enter keyboard scheme drives row presses from `AgentPanelModel` rather than native view focus, so there is nothing to hook a synthetic "open" into. The trigger is still reachable by ←/→ (so its presence/absence and disabled state are visible from the keyboard) but opening it is mouse-only — a deliberate, documented trade-off, not an oversight (`RowActionsModelTests.enterOnTheHighlightedMoreActionsTriggerDoesNotOpenItOrSendAnything` pins it). If a future SwiftUI version adds a way to do this, revisit.
    - **A confirming/busy/completed Done or Close pane pops back OUT of the menu.** `AgentRowView.activeMenuItemSpec` watches `actionState`: while it names `.done` or `.closePane`, that spec is substituted in for the `.moreActions` entry in `visibleButtons`, so the row shows the exact same "Confirm?" / "Stopping…" / "Stopped" capsule (`RowActionButtonView`, same component, same visuals) it always did, in the ⋯ trigger's usual position, for as long as the state lasts. **This is how the safety confirmation survives the menu closing on selection**: the first press (from the menu) can still request a second press, and that second press is a normal capsule click, not a re-opened menu. The trade-off: this reveal is mouse-only too (the keyboard's `usableButtons` list still never includes `.done`/`.closePane`, so ←/→ cannot land the highlight ring on the reappeared capsule) — acceptable since reaching it in the first place already required a mouse click on the menu.
    - **`settleRowActions()`'s "is this completed state stale yet" check** (`AgentPanelModel`) used to ask `RowButtons.usableButtons(for:).contains(button)`; switched to `RowButtons.isPressable(button, on:)` for the same reason as the press guard — Done/Close pane are never in `usableButtons` any more, so the old check would have expired a "Completed"/"Stopped" capsule at the very next status snapshot regardless of whether the dashboard had actually caught up.
    - **Style.** A bare `ellipsis` SF Symbol, sized/tinted like `CopyIdentityButton` (11pt, `.secondary`), `.menuStyle(.borderlessButton)` — deliberately low-visual-weight next to the red/grey capsules, since this is a secondary/housekeeping control, not a primary action.

18. **Agent hierarchy is nested in the main list, not a separate window** (2026-09-25, PO decision). Who-reports-to-whom (`Tree/`: `AgentTree`, `AgentTreeMapper`/`Wire`, `AgentTreeEditing`, `AgentTreeModel`, `AgentTreeDisplayOrder`) briefly had its own "Agent Hierarchy" window (`AgentTreeWindowController`/`AgentTreeView`/`AgentTreeRowView`, plus a `showAgentTreeOnLaunch` debug flag) — all three and the flag are gone. The tree now only changes how the SAME switcher list is grouped/decorated; every existing `AgentListRow`/`AgentPanelModel` consumer is otherwise untouched.
    - **Layout** (`AgentListGrouping`, pure): Needs you stays flat and on top, unchanged (built by `AgentListBuilder` before grouping runs, never touched by it). Below it, while NOT searching and a non-empty tree has loaded: one `.groupHeader(.project)` + its chief's row (`.chief` nesting) + workers indented under it (`.child` nesting, siblings kept in the existing frecency order), server order, a second chief for an already-seen project joining that same group; then a trailing `.groupHeader(.unassigned)` for `tree.unassigned` + `tree.parentGone` (never hidden, `lostParentLabel` shown) + any agent the tree doesn't mention at all. Searching, or before a tree has loaded / an empty tree, falls back to the old flat status-section rows (`AgentListBuilder.flatRows`) — search never nests.
    - **Needs-you dedupe.** A blocked worker (or chief) shows ONLY in Needs you, never a second time nested under its chief — its chief's row instead gets a small "N needs you" hint (`AgentRowNesting.chief(needsYouHint:)`, count of ITS OWN blocked children only).
    - **Cross-project / Air badge carried over verbatim** from the old tree view: `AgentTreeNode.crossProject`/`.machineBadge` ride straight through into `AgentRowNesting.child`/`.unassigned` and `MachineBadgeView` (moved, unedited, from the deleted `AgentTreeRowView.swift`).
    - **`TreeRowActions`** (`Tree/TreeRowActions.swift`) is the ONLY thing that knows about both worlds: it composes the pure, agent-only `RowButtons` (untouched, still has its own tests) with tree-dependent "Report to…"/"Stop reporting" menu items (never offered to a chief; "Stop reporting" only once there's a live parent to detach from). `AgentPanelModel.isPressable`/`usableButtons` delegate here instead of straight to `RowButtons` — if you add a new capsule/menu item, check both files, not just one.
    - **⌘]/⌘[/⌘⌫ and drag-onto-chief** are still `AgentTreeModel.indentSelected`/`outdentSelected`/`attach`/`detach`, unchanged (optimistic move + `treeGeneration` guard against an SSE snapshot landing mid-flight — see its own doc comment); only the trigger surface changed (menu item / keystroke / drop, instead of the old window's row). The row menu's "Report to…"/"Stop reporting" (`RowButton.reportTo`/`.stopReporting`) just point `treeModel.selectedNodeID` at the pressed row first (`AgentPanelModel.press`), since a menu click may not be on the currently-selected row.
    - **Confirm/picker dialogs** (`pendingConfirm` cross-project 409, `pendingChiefPicker` ambiguous Indent) live on `AgentPanelView` now (`.confirmationDialog`s + hidden keyboard-shortcut buttons), ported verbatim off the deleted `AgentTreeView`.

19. **Nest inside each status section, not one group per project** (2026-09-25, PO decision, supersedes gotcha 18's "Layout"/"Needs-you dedupe" bullets — the rest of 18 is unchanged). ~20 of 26 live agents sat in Needs you under the project-group layout (any idle-and-not-yet-triaged agent counts), so the nesting almost never showed. Now the four status sections (`AgentSection`) keep their own order/headers/ranking untouched, unchanged even inside Needs you; nesting happens WITHIN each one instead of only below Needs you.
    - **Layout** (`AgentListGrouping`, pure, rewritten): per section, a worker whose chief is a tree node nests directly under an anchor row for that chief — the chief's own real `AgentListRow.agent(_, nesting: .chief)` row when the chief is ALSO shown in THIS section, else a dimmed `AgentListRow.chiefPlaceholder(AgentTreeNode, section:, needsYouHint:)` (drawn by `ChiefPlaceholderRowView`: label + a literal "chief" tag + the same hint/badge decorations, never a full `AgentRowView` so it can't be mistaken for a live row). A chief whose children land in several sections gets one anchor per section that needs one: its real row in its own section, a placeholder in every other. A top-level entry's position within its section = the best rank (section's own `AgentRanking`) among its members (anchor agent, if real, plus every child) — so one high-ranked child can pull the whole group up past ungrouped agents; children keep the section's ranking order among themselves. `AgentGroupHeader`/`.groupHeader` (the old per-project header) and the old separate Unassigned group are gone entirely; `AgentRowNesting.unassigned` was renamed `.loose` (same fields) since a loose row can now appear inside any section, not just a dedicated one. Searching, or before a tree has loaded / an empty tree, still falls back to the old flat rows (`AgentListBuilder.flatRows`) — search never nests, unchanged.
    - **No more Needs-you dedupe.** Since nesting is section-uniform, a blocked worker of a blocked chief now nests under the chief's real row IN Needs you, instead of being hidden from the group. The "N needs you" hint (`AgentRowNesting.chief(needsYouHint:)`) is unchanged in meaning (count of the chief's own blocked children) but is now drawn identically wherever the chief's anchor (real or placeholder) happens to sit.
    - **Placeholder is keyboard-inert by design.** `AgentListRow.selectableAgentID` is nil for `.chiefPlaceholder` (no real agent behind it to focus/press), so arrow keys skip it exactly like a header — deliberately NOT "jump to the chief's real row elsewhere," since that row may not even be in the current `selectable` list (different section, possibly filtered by search/settings). `TreeDropTarget` still accepts a drop on it (keyed by the chief's own tree id, no `AgentSnapshot` needed), so dragging a worker onto a placeholder attaches it exactly like dropping onto the chief's real row.
    - **`AgentTreeDisplayOrder`** (⌘] "nearest chief above") is intentionally UNCHANGED — it already used the tree's own structural order (parent-gone, then each chief with its children, server order), never the merged list's visual one, so this redesign doesn't touch it.
